# 라인스캔 검사장비 — 1축 엔코더 트리거 하드웨어 설계서

| 항목 | 내용 |
|---|---|
| 대상 | 신규 라인스캔 검사장비 (1축 스캔) |
| 서보 드라이버 | Panasonic **MBDLT25SM** 200 V (MINAS A6S 계열, 400W, **펄스입력형**) |
| 이송 기구 | 리니어모터 + 리니어스케일 (full-closed) |
| 축 제어 | **Ajinextek 모션 보드 (펄스 출력)** — AXL 통합 |
| 트리거 모듈 | Ajinextek **SIO-HPC4L** (엔코더 4CH, 차동 입력 ~5 MHz) |
| 트리거 피치 | **5.0 µm** |
| 트리거 출력 | 5 V TTL (push-pull) → 카메라 Trigger IN |

> **개정 이력**
> - Rev.1 : 초안 (FASTECH Ez-ML 유지, 드라이버 계열 미확정)
> - **Rev.2 : 실물 확인 반영. FASTECH Ez-ML-PE-PAN 제거, X4를 아진 커넥터로 직결하는 구성으로 전면 변경**
> - **Rev.3 : 실장 UPP는 0.1 µm가 아니라 1 µm. 아래 §4.2의 0.1 µm는 설계 권장값이며, 현재 장비는 그 값으로 만들어져 있지 않습니다. §4.2 말미의 "실장 현황" 참조**

## 1. 구성 변경의 배경

### 실물 확인 결과

현장 사진으로 다음이 확인되었습니다.

| 항목 | 확인 내용 |
|---|---|
| 드라이버 라벨 | **MBDLT25SM 200 V** |
| 네트워크 모듈 | **FASTECH Ez-ML-PE-PAN** (Ezi-MotionLink **Plus-E**), S/N 230306572 |
| 모듈 I/F | Ethernet-IN / OUT 데이지체인, 로터리 노드주소 스위치 2개, 표시 "02" |
| 드라이버 커넥터 | X1(mini USB), X2, X3, X5 육안 확인 |

**핵심 발견: 이더넷은 드라이버가 아니라 FASTECH 애드온 모듈이 제공하고 있었습니다.**
MBDLT25SM 자체는 모델코드의 `S`가 가리키는 대로 **평범한 A6S 펄스입력형 드라이버**입니다. Ezi-MotionLink Plus-E는 Panasonic MINAS(A/A3/A4/A5/A6)의 지령 I/O 커넥터에 플러그인되어 펄스 지령을 만들어 주는 네트워크 모션 컨트롤러입니다.

### 결정

**Ez-ML 모듈을 제거하고 X4를 아진 커넥터로 직결한다.**

이로써 초안의 두 가지 미결 리스크가 동시에 해소됩니다.
- 드라이버 계열 불명 → A6S 펄스형으로 확정, 분주 출력 보유 가능성 높음
- X4 커넥터 경합 → 모듈 제거로 소멸

## 2. 시스템 구성

```
 ┌─ PC : SEQApp + AXL ─────────────────────────────────┐
 │                                                      │
 │  [아진 모션 보드]                                     │
 │     PULS± / SIGN±  ──────────────┐                   │
 │     SRV-ON, A-CLR, CL ───────────┤                   │
 │     ALM, S-RDY, INP  ◀───────────┤                   │
 │                                  │                   │
 │  [아진 SIO-HPC4L]                │                   │
 │     ENC A±/B±/Z±     ◀───────────┤                   │
 │     TRIG OUT ────────────────────┼──▶ [라인스캔 카메라]│
 │                                  │      pin1 Trigger IN│
 │  [아진 DIO]                      │                   │
 │     리밋 / 원점 / EMG ───────────┤                   │
 └──────────────────────────────────┼───────────────────┘
                                    │ X4 (50pin)
                          ┌─────────▼─────────┐
                          │   MBDLT25SM       │
                          │   MINAS A6S 400W  │
                          └───┬───────────┬───┘
                          X5  │           │ U/V/W
              [리니어스케일]──┘           └──▶ [리니어모터]
                 (full-closed 피드백)
```

### 이 구성의 이점

| 항목 | 효과 |
|---|---|
| 소프트웨어 | **SEQApp 기존 AXL 코드 재사용.** FASTECH 라이브러리 통합 불필요 |
| 커넥터 | X4 경합 없음 — 지령·상태·분주출력을 한 커넥터에서 |
| 벤더 | 모션·트리거·DIO 모두 아진 = AXM / AXC / AXD 단일 라이브러리 |
| 동기 | 지령과 트리거가 같은 PC·같은 라이브러리 → 스캔 시퀀스 일원화 |

## 3. ★ 핵심 개념 — 지령 분해능과 트리거 분해능은 **독립**입니다

설계에서 가장 혼동하기 쉬운 지점입니다.

| | 지령 펄스 (아진 → 드라이버) | 분주 출력 (드라이버 → HPC4L) |
|---|---|---|
| 방향 | 아진 → 드라이버 | 드라이버 → 아진 |
| 의미 | "이만큼 가라" (목표) | "이만큼 갔다" (실제) |
| 분해능 결정 | 전자기어 Pr0.08~0.10 | 분주 설정 (Pr0.11 계열) |
| 필요 정밀도 | **낮아도 됨** — 서보가 보간 | **높아야 함** — 트리거 위치 정확도 |
| 권장값 | P_cmd = 0.5 ~ 1.0 µm | UPP = 0.1 µm |

**트리거는 반드시 분주 출력(실제 위치)에서 뽑습니다.** 지령 펄스에서 트리거를 만들면 추종오차·정정거동이 반영되지 않아 무의미합니다.

## 4. 수치 설계

### 4.1 제약 조건

| # | 제약 | 값 |
|---|---|---|
| C-1 | 트리거 피치가 **정수 엔코더 카운트** | `5.0 µm / UPP = 정수` |
| C-2 | 드라이버 분주 출력 상한 | **4 Mpps** |
| C-3 | HPC4L 차동 입력 상한 | **5 MHz** |
| C-4 | 드라이버 지령 펄스 입력 상한 | **4 Mpps** (라인드라이버) |
| C-5 | 아진 모션 보드 펄스 출력 상한 | 보드별 — **확인 필요** |

### 4.2 트리거측 — UPP 후보

`UPP` = 4체배 후 1카운트 거리 · `f_A` = 분주 출력 A상 주파수 = `v / (4 × UPP)`

| UPP | 5 µm의 카운트 | 피치 조정 스텝 | f_A @300 mm/s | @500 mm/s | @800 mm/s |
|---|---|---|---|---|---|
| 1.0 µm (실장) | 5 | 20 % | 75 kHz | 125 kHz | 200 kHz |
| 0.5 µm | 10 | 10 % | 150 kHz | 250 kHz | 400 kHz |
| 0.25 µm | 20 | 5 % | 300 kHz | 500 kHz | 800 kHz |
| **0.1 µm** | **50** | **2 %** | 750 kHz | **1.25 MHz** | 2.0 MHz |
| 0.05 µm | 100 | 1 % | 1.5 MHz | 2.5 MHz | 4.0 MHz ⚠ |
| 0.025 µm | 200 | 0.5 % | 3.0 MHz | 5.0 MHz ❌ | ❌ |

**권장: UPP = 0.1 µm** (피치 = 정확히 50 카운트, 500 mm/s에서 4 Mpps 대비 여유 3.2배)

치수 측정을 병행하면 UPP 0.025 µm(ε 0.5 %)로 올리되 **최고속이 300 mm/s로 제한**됩니다.

#### 실장 현황 (2026-09)

현재 장비는 **UPP = 1 µm**로 구성되어 있습니다. EzManager의 CounterAgent가 채널 0에
`Count Unit/Pulse 0.001`을 표시하고, `AxcMotSetMoveUnitPerPulse(0, 0.0010)`으로 쓰고
있는 것이 EzSpy 트레이스로 확인되었습니다. `SEQ04_ScanTrigger.cpp`의
`SCANTRIGGER_ENC_UNIT_MM`도 이 값에 맞추었습니다.

그 결과 **트리거 피치는 1 µm 단위로만 지정할 수 있습니다.** 위 표의 "피치 조정 스텝"
20 %가 그 의미이며, 실제로 걸리는 제약은 다음과 같습니다.

| 원하는 픽셀 분해능 | 1 µm 격자에서 | 결과 |
|---|---|---|
| 5.0 µm | 5 카운트 | 정확 |
| 10.0 µm | 10 카운트 | 정확 |
| **18.1 µm** | 18.1 카운트 | **불가** — 18 µm(−0.55 %) 또는 19 µm(+4.97 %) |

`ScanTriggerValidate()`는 정수가 아닌 피치를 `SCANTRIGGER_VALIDATE_PITCH_FRACTION`
("PITCH FRAC")으로 거부하고, MMI의 카운트 칸에 `18.10 !`처럼 표시합니다. 보드가 조용히
반올림해서 스캔 전체에 걸쳐 누적 오차를 만드는 것보다 낫다는 판단입니다.

18.1 µm를 그대로 쓰려면 §4.2의 권장대로 드라이버 분주 출력(`Pr0.11`)을 조정해
UPP를 0.1 µm로 낮추어야 합니다. 그러면 18.1 µm = 181 카운트로 정확히 떨어집니다.

### 4.3 지령측 — P_cmd 후보

`f_cmd = v / P_cmd`

| P_cmd | f_cmd @300 mm/s | @500 mm/s | @800 mm/s | 판정 |
|---|---|---|---|---|
| 0.1 µm | 3.0 Mpps | 5.0 Mpps ❌ | ❌ | 과도 |
| 0.2 µm | 1.5 Mpps | 2.5 Mpps | 4.0 Mpps ⚠ | 가능 |
| **0.5 µm** | 0.6 Mpps | **1.0 Mpps** | 1.6 Mpps | **권장** |
| 1.0 µm | 0.3 Mpps | 0.5 Mpps | 0.8 Mpps | 여유 |

**권장: P_cmd = 0.5 µm.** 등속 스캔이므로 지령이 거칠어도 서보가 매끄럽게 추종합니다. 아진 보드 출력 상한(C-5)에도 여유가 큽니다.

### 4.4 라인스캔은 TDI보다 관대합니다

| | TDI 256단 (기존 장비) | 라인스캔 (신규) |
|---|---|---|
| 피치 오차 ε의 영향 | **smear = 256 × ε** | 이미지 종횡비 오차 = ε |
| ε = 1 % 일 때 | 2.56 px 뭉갬 | 100 px당 1 px 신축 |
| 허용 ε | 0.2 % | **0.5 ~ 2 %** (용도별) |

- 외관 검사만 → ε 2 % 이내 실용상 무해 → UPP 0.1 µm로 충분
- 치수 측정 병행 → ε 0.5 % 이내 → UPP 0.025 µm + 속도 제한

### 4.5 속도 상한

```
v_max = 카메라 라인레이트 × 5.0 µm
```

| 라인레이트 | v_max | UPP 0.1 µm의 f_A | P_cmd 0.5 µm의 f_cmd |
|---|---|---|---|
| 50 kHz | 250 mm/s | 625 kHz ✅ | 500 kpps ✅ |
| 100 kHz | 500 mm/s | 1.25 MHz ✅ | 1.0 Mpps ✅ |
| 150 kHz | 750 mm/s | 1.88 MHz ✅ | 1.5 Mpps ✅ |
| 200 kHz | 1,000 mm/s | 2.5 MHz ✅ | 2.0 Mpps ✅ |

권장 조합(UPP 0.1 µm / P_cmd 0.5 µm)은 카메라 200 kHz까지 모든 제약을 만족합니다.

> 오버트리거(트리거가 카메라 라인주기보다 빨리 도착)는 라인 누락 → 이미지 압축으로 나타납니다. **v_max에 20~30 % 마진**을 두십시오.

## 5. X4 신호 분배

X4 50핀을 세 계통으로 나누어 아진 보드에 배분합니다.

### 5.1 지령·제어 (아진 모션 보드 → 드라이버)

| 신호 | 내용 | 방향 |
|---|---|---|
| PULS1 / PULS2 | 지령 펄스 (라인드라이버 권장) | 아진 → 드라이버 |
| SIGN1 / SIGN2 | 지령 방향 | 아진 → 드라이버 |
| SRV-ON | 서보 ON | 아진 → 드라이버 |
| A-CLR | 알람 클리어 | 아진 → 드라이버 |
| CL | 편차카운터 클리어 | 아진 → 드라이버 |
| POT / NOT | 정/역 오버트래블 | 아진 → 드라이버 |
| COM+ / COM− | I/O 24 V 전원 | — |

### 5.2 상태 (드라이버 → 아진 모션 보드 / DIO)

| 신호 | 내용 |
|---|---|
| ALM+ / ALM− | 서보 알람 |
| S-RDY+ / S-RDY− | 서보 레디 |
| INP+ / INP− | 위치결정 완료 |
| BRK-OFF+ / BRK-OFF− | 브레이크 해제 (리니어모터는 해당 시) |

### 5.3 분주 출력 (드라이버 → SIO-HPC4L) ★

| 신호 | HPC4L |
|---|---|
| OA+ / OA− | ENC A+ / A− |
| OB+ / OB− | ENC B+ / B− |
| OZ+ / OZ− | ENC Z+ / Z− |
| SG (신호 GND) | GND |

- **실드 트위스트 페어 3쌍**, 실드는 드라이버측 1점 접지
- 차동 전송이므로 노이즈 내성 양호. 서보 전력선과 분리 배선
- Z상은 원점 복귀용 (스캔 트리거에는 미사용이나 원점 재현성 확보에 유리)

> ⚠️ **X4 핀 번호는 본 문서에 기재하지 않았습니다.** 검색으로 원문 대조를 하지 못했고, 오결선 시 손상 위험이 있어 **해당 모델 매뉴얼의 X4 핀 배치도로 직접 확인**하십시오. 신호 이름은 MINAS A5/A6 공통 명칭입니다.

### 5.4 트리거 출력 (SIO-HPC4L → 카메라)

| HPC4L | 카메라 Control I/O |
|---|---|
| TRIG OUT 0 | pin 1 — Trigger IN |
| GND | pin 3 — DC GND |

- 5 V TTL push-pull ↔ 카메라 V_IH 2~5 V → **레벨 호환, 풀업 불필요**
- **케이블 1 m 초과 시 출력단에 직렬 33~47 Ω** (반사·링잉 억제). 링잉이 입력 임계값을 넘나들면 1펄스가 2펄스로 계수됩니다
- 실드 트위스트 페어, 2 m 이내 권장
- 접지 전위차 우려 시 **고속 포토커플러(6N137급, ~10 Mbps)** 절연. 일반 포토커플러는 응답 부족으로 사용 불가
- 카메라측 핀 배열도 매뉴얼 대조 필요

## 6. 아진 보드 요구 사양

| 기능 | 요구사항 |
|---|---|
| 모션 1축 펄스 출력 | 라인드라이버 출력, **≥2 Mpps** (P_cmd 0.5 µm · 1,000 mm/s 기준), `AxmMotSetPulseOutMethod` 지원 |
| 엔코더 트리거 | **SIO-HPC4L** — 차동 입력 5 MHz, periodic 모드 위치주기 트리거 |
| DIO | 서보 ON/알람/리밋/원점/EMG |

AXL 단일 라이브러리로 통합 제어합니다.

| 계열 | 담당 |
|---|---|
| **AXM** | 축 지령 (`AxmMotSetPulseOutMethod`, `AxmSignalSetServoOnLevel`, 프로파일 이동) |
| **AXC** | 트리거 (`AxcTriggerSetFunction` periodic mode) |
| **AXD / AXA** | DIO |

### 펄스 출력 방식

`AxmMotSetPulseOutMethod(lAxisNo, uMethod)`

| uMethod | 방식 |
|---|---|
| 0~3 | 1-pulse (PULSE + DIR) — Panasonic 표준, **권장** |
| 4~7 | 2-pulse (CW / CCW) |
| 8~9 | 2-phase (A/B 90°) |

드라이버측 지령 펄스 입력 형식(Pr0.05~0.07)과 일치시켜야 합니다.

## 7. 서보 파라미터

| 파라미터 | 설정 | 목적 |
|---|---|---|
| 제어 모드 | 위치 제어 (펄스 지령) | 아진 펄스 지령 수신 |
| 피드백 | full-closed (리니어) + X5 외부 스케일 | 리니어모터 위치 제어 |
| Pr0.05~0.07 | 지령 펄스 입력 형식 | 아진 출력 방식과 일치 |
| Pr0.08~0.10 | 전자기어 | **P_cmd = 0.5 µm** 가 되도록 |
| 분주 출력 소스 | **external scale** | X4 출력이 스케일 위치를 반영 ★ |
| Pr0.11 | 분주 출력 펄스 수 | **UPP = 0.1 µm** 가 되도록 |
| Pr0.12 | 출력 방향 반전 | 스캔 방향에 맞춰 (HPC4L `AxcSignalSetEncReverse`로도 대응 가능) |

> **Pr0.11은 "모터 1회전당 출력 펄스 수"로 정의된 회전형 기준 파라미터입니다.** 리니어모터/full-closed 구성에서 분주비가 어떤 파라미터로 결정되는지는 해당 모델 매뉴얼에서 확인해야 합니다. 스케일 펄스를 무분주로 그대로 출력할 수 있다면 양자화 오차가 없어 가장 유리하므로 우선 검토하십시오.

### 스캔 프로파일

```
가속 → 속도 정정(settling) → [트리거 구간 진입] → 등속 스캔 → [구간 이탈] → 감속
```

트리거 Block 구간을 등속 구간 안쪽으로 설정하고, 진입 전 정정이 끝나도록 조주 거리를 확보하십시오.

## 8. SIO-HPC4L 설정 (periodic mode)

버퍼를 사용하지 않는 하드웨어 위치주기 트리거입니다. **트리거 개수 제한이 없습니다.**

> **구현 완료** — `SEQApp/Hardware/CLASS_TRIGGER.{h,cpp}`의 `CAjinTrigger`에 반영되어 있고
> `FUNC_Init.cpp`의 `InitIO()`에서 전역 `AjinTrigger`로 생성됩니다.
> 아래 raw API 시퀀스는 참고용이며, 실제 호출은 `PERIODIC_TRIG_CFG`를 채워
> `AjinTrigger->StartPeriodicTrigger(cfg)` 한 번으로 끝납니다.
>
> ```cpp
> PERIODIC_TRIG_CFG cfg;              // 기본값: UPP 1um, 피치 5um, 폭 2us, High active
> cfg.lChannelNo = 0;
> cfg.dScanStart = 0.0;
> cfg.dScanEnd   = 200.0;             // -> 40,000 트리거
> AjinTrigger->ResetScanOrigin(0);
> AjinTrigger->StartPeriodicTrigger(cfg);
> ```
>
> `StartPeriodicTrigger()`는 **피치가 정수 엔코더 카운트가 아니면 거부**하고
> 반올림으로 생길 상대오차를 로그에 출력합니다 (3.1절의 C-1 제약을 코드로 강제).
> 펄스폭 1 µs 미만, 채널 범위 초과, 구간 역전도 같은 방식으로 막습니다.

```cpp
AxcTriggerSetEnable       (ch, 0);          // 설정 중 출력 정지
AxcTriggerSetEncoderInput (ch, encInput);   // 엔코더 입력 0~3
AxcSignalSetEncInputMethod(ch, 0x03);       // A/B상 4체배
AxcSignalSetEncSource     (ch, 0x00);       // A/B상 신호
AxcSignalSetEncReverse    (ch, bReverse);   // 진행 방향

AxcMotSetMoveUnitPerPulse (ch, 0.0010);     // UPP = 1 um = 0.001 mm (실장값)
AxcTriggerSetFunction     (ch, 0x03);       // ★ periodic mode (위치 주기)

WORD w;                                     // ★ 이 두 줄이 없으면 출력이 나오지 않음
AxcKeGetCommandData16     (ch, 22,  &w);    //   채널 레지스터 0x16 읽기
AxcKeSetCommandData16     (ch, 150, w | 2); //   150 = 0x96 = 0x16 | 0x80 (쓰기 별칭), 비트 1 set
AxcTriggerSetBlock        (ch, start, end, 0.005);  // 구간 + 피치 5 um
AxcTriggerSetDirectionCheck(ch, 0x01);      // 증가 방향에서만

AxcTriggerSetTriggerOutport (ch, 0x1);      // Trigger Out 0
AxcTriggerSetTime           (ch, 2.0);      // 펄스 폭 2 us (카메라 최소 1 us)
AxcTriggerSetLevel          (ch, 1);        // High active
AxcTriggerSetTriggerOutCount(ch, 1);        // 주기당 1발

AxcTriggerSetTriggerCountClear(ch);
AxcTriggerSetEnable           (ch, 1);      // 활성화
```

- 스캔 원점: `AxcStatusSetActPos(ch, 0.0)`
- 정지: `AxcTriggerSetEnable(ch, 0)`

> **SIO-HPC4L은 mm 단위를 받지 않습니다.** `AxcMotSetMoveUnitPerPulse`는 `AXC.h`에
> `// API for SIO-CN2CH only`로 명시되어 있고, 이 보드에서는 **성공을 반환하고 아무것도
> 하지 않습니다.** CounterAgent의 `Count Unit/Pulse`도 `Setting`을 눌러도 1.000에
> 머뭅니다. 따라서 `AxcTriggerSetBlock` / `AxcTriggerSetPosPeriod` /
> `AxcStatusSetActPos`에 넣는 값은 전부 **raw 엔코더 카운트**여야 합니다.
> mm를 그대로 넣으면 블록이 카운터가 도달하지 못하는 곳(1/UPP 배 먼 곳)에 놓이고,
> 스테이지가 블록에 들어가지 못해 트리거가 한 발도 나오지 않습니다.
>
> **동작 확인 완료 (2026-09).** 아래 설정으로 오실로스코프에서 트리거 출력이 확인되었습니다.
>
> | 항목 | 값 |
> |---|---|
> | 카운터 단위 | raw 카운트 (1 카운트 = 1 µm) |
> | 블록 | 100,000 ~ 600,000 카운트 (100 ~ 600 mm) |
> | 피치 / 주기 | 18 카운트 (18 µm) |
> | 펄스 폭 | 10 µs |
> | Active Level | 1 (High) → 카메라는 **Rising Edge** |
> | Direction Check | 1 (CW) |
> | Encoder | Method 3 (A/B 4체배), Source 0, **Reverse 1** |
> | 라인레이트 / 속도 | 11,050 Hz / 198.9 mm/s |
> | 측정 주행량 | 500.0050 mm (지령 500.0000 mm, 오차 0.001 %) |
>
> **엔코더 방향이 반대입니다.** 100 mm → 600 mm 지령에 카운터는 +100000 → -399998로
> 움직였습니다. 크기는 500.0040 mm 대 500.0000 mm로 정확하므로 스케일·배선·1 µm
> 분해능은 모두 정상이고 **부호만** 반대입니다. 리니어 스케일의 A/B상이 모터 정방향
> 기준으로 뒤바뀌어 있습니다. 상승 방향으로 무장된 블록은 하강하는 카운터의 모든
> 위치를 거부하므로 트리거가 한 발도 나오지 않습니다.
> → `AxcSignalSetEncReverse(ch, 1)` (`SCANTRIGGER_ENC_REVERSE = true`)로 보정.
>
> 확인된 사실 (2026-09, 오실로스코프 + CounterAgent):
> - 트리거 출력은 CON1 1-2번에 나옵니다. Active Level을 바꾸면 0 V ↔ 5 V로 바뀝니다.
> - 즉 배선·핀·출력단은 정상이며, 문제는 항상 컴퍼레이터가 발화하지 않은 것이었습니다.
> - `AxcTriggerSetEnable`은 출력단 최종 게이트입니다. Disable 상태에서는 강제 출력도
>   핀에 도달하지 않습니다.
>
> **`AxcKe*CommandData16` 한 쌍에 대하여** — `AXDev.h`에 선언만 있고 레지스터도 비트도
> 문서화되어 있지 않습니다. 그러나 EzManager의 CounterAgent가 "Apply"할 때 EzSpy에
> 정확히 이 두 호출이 찍히고, **이 두 줄이 빠지면 나머지 설정이 모두 성공을 반환해도
> 트리거 핀이 전혀 동작하지 않습니다.** 같은 시퀀스가 이 프로젝트의
> `CLASS_AjinCounter::SetTriggerPosition()`(절대위치 모드)에도 이미 들어 있습니다.

카메라측: `Trigger Mode` = On · `Trigger Source` = External · `Trigger Activation` = **Rising Edge**
(High active + push-pull이므로 논리 반전 없음)

> periodic mode(0x03)와 `SetBlock`/`SetPosPeriod`는 AXC 헤더에 SIO-HPC4 전용으로 명시되어 확실합니다.

### ★ 실측 — 이 보드에서 쓸 수 없는 읽기 API 2종 (2026-09-29)

스캔 로그에서 확인된 값입니다. **둘의 원인이 서로 다르며, 대응도 다릅니다.**

| API | 증상 | 원인 | 새 AXL로 해결되는가 |
|---|---|---|---|
| `AxcTriggerReadTriggerCount` | `GetProcAddress` 실패 | 설치된 **AXL 4.2.0.2의 export에 없음** (`Library/`의 AXL.dll에는 5개 모두 존재) | **예** — AXL 교체로 복구 |
| `AxcStatusGetChannel` | `1054` 반환 | **`AXT_RT_NOT_SUPPORT_VERSION` (Unsupported Hardware)** — SIO-HPC4L이 구현하지 않음 | **아니오** — 보드 문제 |

`AxcStatusGetChannel`은 `AXC.h`에 `// API for SIO-CN2CH only` 표기가 **없습니다.** 그럼에도
SIO-HPC4L은 거부합니다. `AxcMotSetMoveUnitPerPulse`와 같은 종류의 함정이며, 다만 그쪽은
*성공을 반환하고 아무것도 하지 않은* 반면 이쪽은 정직하게 에러를 돌려줍니다.

**결론 — 현재 구성(SIO-HPC4L + AXL 4.2.0.2)에서는 출력 펄스에 대한 소프트웨어 검증 수단이
하나도 없습니다.** 개수도(`ReadTriggerCount` 부재), 핀 레벨도(`StatusGetChannel` 미지원)
읽을 수 없습니다. V-3 검증은 AXL 교체 전까지 **스코프 또는 카메라 Strobe OUT 계수로만**
가능합니다.

### SIO-HPC4 트리거 모드 — 벤더 가이드 기준 (2026-09-29 확인)

출처: Ajinextek **"CS_Function_Example Guide Manual Rev 1.0 — Counter Trigger"** 2장.

> Trigger 출력 방법으로는 **Timer Mode(Count), Timer Mode, Absolute Mode, Period Mode, One Shot Trigger 총 5가지**를 지원한다.

| 모드 | 위치 동기 | 피치 양자화 | 용도 |
|---|---|---|---|
| **Period Mode** | ○ 엔코더 비교기 | 엔코더 1 count (= 1 µm) | 현재 사용 |
| **Timer Mode** | ✕ 자유 발진 | 정수 Hz | 엔코더로 표현 못 하는 피치 |
| **Timer Mode (Count)** | ✕ 자유 발진 | 정수 Hz | 위 + **펄스 개수 하드웨어 고정** |
| Absolute Mode | ○ 위치 배열 | UnitPerPulse | 개별 위치 촬상 |
| One Shot | — | — | 강제 1발 |

`AxcTableTriggerDistancePatternShot` / `AxcTriggerDistancePatternShot`(= `CCGC_CNT_DISTANCE_PERIODIC_TRIGGER`)은 **CNT_RECAT_SC_10 전용**이며 HPC4에는 없습니다.

#### Timer Mode (Count) — 펄스 개수를 하드웨어가 셉니다

> AxcKeSetCommandData32 함수를 이용하여 Trigger 출력 개수를 설정하며 내부 인자값 중 Command는 모듈 기준 **0번 채널[244], 1번 채널[245], 2번 채널[246], 3번 채널[247]**로 입력하여 사용한다.

Timer mode에는 블록이 없어 소프트웨어가 창을 여닫아야 하고, 그 가장자리는 SEQ 사이클 1회분(200 mm/s · 18 µm에서 약 **111 라인**)만큼 흔들립니다. 개수를 하드웨어에 맡기면 **라인 수는 정확**해지고 남는 오차는 이미지 시작 위치의 어긋남뿐입니다.

### ★ 레지스터 설정 — 벤더 가이드가 명문화

EzSpy 추적으로 찾아낸 레지스터 조작이 가이드에 **산문으로** 기재되어 있습니다.

> (1) **Trigger Mode, Active Level, Direction Check에 따라 레지스터의 값이 변경**된다.
> - Trigger Mode → **4, 5번 비트**
> - Active Level → **0번 비트**
> - Direction Check → **6, 7번 비트**
>
> (2) AxcKeGetCommandData16 함수로 특정 어드레스 값을 읽어 **1번 비트를 1로 변경**하여 입력한다. **1번 비트는 트리거 출력에 영향을 주는 비트로, PC 종료 시 0으로 초기화되므로 반드시 변경**해야 한다.
>
> (3) **0, 1번 채널은 22(Command)에서 읽어 150(Command)에 설정**하며, **2, 3번 채널은 54(Command)에서 읽어 182(Command)에 설정**한다.

두 가지가 확정되었습니다.

1. **bit 1은 추측이 아니라 필수 절차**입니다. "PC 종료 시 0으로 초기화"가 이 프로젝트가 며칠을 쓴 증상 — 모든 호출이 성공을 반환하는데 출력 핀은 죽어 있던 — 의 정체입니다.
2. **채널 2, 3은 주소가 다릅니다.** 코드에 22/150이 하드코딩되어 있었고, 채널 2로 옮겼다면 채널 0의 레지스터를 쓰고 자기 출력은 죽은 채 아무 에러도 나지 않았을 것입니다. → `TriggerRegApply()`로 수정.

또한 **모드가 bits 4-5에 실려 되읽힌다**는 점이 중요합니다. API 모드 번호가 맞는지를 하드웨어에 직접 물을 수 있습니다.

#### ⚠ 모드 번호 — AXC.h와 가이드 예제가 불일치

| | Timer | Absolute | Period |
|---|---|---|---|
| **AXC.h** (HPC4 항목) | `0x01` | `0x00` ram / `0x02` fifo | **`0x03`** |
| **가이드 예제** | `0x00` | `0x02` | `0x02` ← 주석은 "절대위치모드" |

가이드 예제 쪽이 신뢰도가 낮습니다. Timer 예제 2개가 주석까지 동일한 복붙이고, Period 예제의 주석은 절대위치모드라고 적혀 있습니다. 무엇보다 **AXC.h의 `0x03`(periodic)은 이 장비에서 스코프로 검증**되었습니다. 따라서 AXC.h를 따르되, `AxcTriggerGetFunction`과 레지스터 bits 4-5를 **둘 다 되읽어** 불일치를 로그로 드러냅니다.

### ★ 트리거 간격 하한 — 듀티 50 %

> 연속적으로 Trigger를 출력 시에는 해당 Trigger의 출력시간, 속도 대비 적절한 주기를 사용해야 출력될 Trigger가 겹치지 않고 정상적으로 출력된다. 적절한 주기는 **Trigger가 출력되는 동안 이동거리의 2배(Trigger 출력시간 × 속도 × 2)**의 값을 권장한다.

가이드의 실측 예시:

| 조건 | 듀티 | 결과 |
|---|---|---|
| 펄스 1000 µs, 100,000 pulse/s, 주기 100 pulse | 100 % | **50개 중 21개만 출력** |
| 펄스 1000 µs, 50,000 pulse/s, 주기 100 pulse | 50 % | 50개 중 50개 출력 |

즉 **듀티 ≤ 50 %**. 초과 시 트리거가 합쳐지는 게 아니라 **누락**됩니다.

현재 코드의 `SCANTRIGGER_PULSE_MAX_DUTY = 0.4`는 이보다 엄격하므로 안전합니다. 현재 설정(5 µs / 200 mm/s / 18 µm)은 듀티 5.6 %.

### ✅ 펄스폭 하한 — **1 µs 실측 확인** (2026-09-30)

가이드 `AxcTriggerSetTime` 설명에 **범위 [10 ~ 50,000] µs**가 적혀 있으나, 이는 **SIO-CN2CH 항**이며 HPC4 항에는 범위 표기가 없습니다.

**SIO-HPC4L에서 1 µs까지 출력 확인 완료.** CN2CH의 하한은 이 보드에 적용되지 않습니다. 코드의 `SCANTRIGGER_PULSE_MIN_US = 1.0`은 추정이 아니라 실측 하한입니다.

이로써 듀티 제약이 사실상 풀립니다.

| 라인레이트 | 주기 | 1 µs 듀티 | 40 % 캡에서의 최대 펄스폭 |
|---|---|---|---|
| 40 kHz | 25.000 µs | 4.0 % | 10.000 µs |
| 64 kHz | 15.625 µs | **6.4 %** | 6.250 µs |
| 100 kHz | 10.000 µs | 10.0 % | 4.000 µs |
| 253 kHz | 3.945 µs | 25.3 % | 1.578 µs |
| 400 kHz | 2.500 µs | 40.0 % | 1.000 µs |

**1 µs 펄스 기준 상한**

| 제약 | 한계 |
|---|---|
| 우리 40 % 캡 | 400 kHz |
| Ajinextek 50 % | 500 kHz |
| **`AxcTriggerSetFreq` 상한** | **500 kHz** ← 실질 제약 |

즉 1 µs를 쓰면 듀티가 아니라 **`AxcTriggerSetFreq`의 500 kHz가 먼저 걸립니다.**

`AxcTriggerGetTime` 되읽기는 유지합니다. 호출 1회 비용으로, 검증한 폭과 보드가 실제로 쥔 폭 사이를 지키는 유일한 수단이며, 다른 보드나 다른 AXL이 이 보드처럼 동작하리란 보장이 없습니다.

### 확인 방법 — 벤더 권장

> Trigger 출력이 정상적으로 동작하는지 확인을 위해서는 **Trigger Level을 변경하여 상시 출력 전압값이 변하는지 확인**한다.

이 프로젝트에서 실제로 출력단을 처음 분리해낸 방법과 동일합니다.

## 9. 리스크 — Ez-ML 제거로 잃는 것

### R-1. 리니어모터 자극 검출 (magnetic pole detection) — **최우선**

리니어모터는 전원 투입 후 **자극(magnetic pole) 위치를 알아야 통전할 수 있습니다.**

- 절대치 스케일 + 자극위치 저장 구성이면 자동 복원
- 증분 스케일이면 **매 전원투입마다 자극검출 동작**이 필요

**Ez-ML 모듈이 이 시퀀스를 대행하고 있었다면, 모듈 제거 후 드라이버 자체 기능 + 아진 시퀀스로 재구현해야 합니다.**

→ Panasonic A6 리니어 모드의 자극검출 파라미터·시퀀스를 확인하고, 필요 시 SEQApp 초기화 루틴에 반영하십시오. **모듈 제거 전에 반드시 확인할 항목입니다.**

### R-2. Ez-ML의 궤적 생성·네트워크 기능 상실

1축 등속 스캔이므로 아진 보드의 프로파일 생성으로 충분합니다. **실질 영향 없음.**

### R-3. 다른 축이 Ez-ML 네트워크에 물려 있는 경우

사진의 Ethernet-OUT과 노드주소 "02"는 **데이지체인에 다른 노드가 존재할 가능성**을 시사합니다. 이 축만 분리할 때 나머지 노드의 통신이 끊기지 않는지 확인이 필요합니다.

### R-4. X4 배선 재작업

Ez-ML 전용 하네스를 아진 보드용 하네스로 교체해야 합니다. 신호 수가 많으므로(지령 4 + 제어 5 + 상태 8 + 분주 7) **50핀 커넥터 압착 하네스를 제작**하는 편이 확실합니다.

## 10. 검증 절차

| # | 항목 | 방법 | 판정 |
|---|---|---|---|
| V-1 | 분주 출력 확인 | X4 OA/OB를 스코프 차동 프로브로 관측, 알려진 거리 D 이동 후 펄스 계수 | `D / 펄스수` = 설계 UPP |
| V-2 | 카운터 검증 | `AxcStatusSetActPos(ch,0)` → 100 mm 이동 → `AxcStatusGetActPos` | 100.000 mm |
| V-3 | **트리거 개수** ★ | `AxcTriggerSetTriggerCountClear` → 200 mm 스캔 → `AxcTriggerReadTriggerCount` | **40,000** (200mm/5µm) |
| V-4 | 트리거 인식 | HPC4L 출력 + 카메라 **Strobe OUT(pin4)** 2채널 동시 관측, 속도 단계 상승 | 최고속까지 누락·중복 없음 |
| V-5 | 지령 추종 | 등속 구간에서 지령 위치 vs 실제 위치 편차 모니터 | 편차 안정 |
| V-6 | 이미지 검증 | 격자 타깃 스캔 → 스캔방향/어레이방향 치수비 | 종횡비 오차 = ε |

**V-3이 핵심입니다.** 실제 피치 = 이동거리 / 트리거수 이고, 설계값과의 차이가 곧 ε입니다. 이미지 촬상보다 빠르고 정량적입니다.

> **2026-09-29 현재 V-3은 소프트웨어로 불가능합니다.** `AxcTriggerReadTriggerCount`가
> 설치된 AXL 4.2.0.2에 없습니다(8절 실측 표 참조). 카메라 Strobe OUT 또는 HPC4L
> 출력선을 외부 카운터로 계수하십시오. AXL을 `Library/`의 버전으로 교체하면
> 이 항목은 소프트웨어로 되돌아옵니다.

### 2번에 대하여 — 현재까지 확인된 것

트리거 실동작에서 500 mm 이동에 **500,000 카운트**가 측정되었습니다. 4체배 후 1 µm/카운트,
즉 **드라이버 분주 출력의 A/B 신호 주기가 4 µm**입니다. 다만 이 측정만으로는 두 경우를
구분할 수 없습니다.

| 경우 | 분주 출력 주기 | UPP 0.1 µm |
|---|---|---|
| (a) 스케일 원 분해능이 1 µm이고 분주는 1:1 통과 | 4 µm | **불가** |
| (b) 스케일이 더 곱고 드라이버가 나눠서 출력 중 | 4 µm | 가능 |

**구분 방법:** PANATERM 모니터에서 외부 스케일 피드백 펄스를 읽고 100 mm를 이동시켜
차이를 확인합니다. 차이가 100,000이면 (a), 그보다 크면 (b)입니다.

기본값이 1:1 통과인 점을 감안하면 (a)일 가능성이 높으나, 측정 전까지는 확정이 아닙니다.

## 부록. 기존 TDI 장비 대비 개선점

기존 VT-16K5X-H140A-256 장비의 블러 원인 조사에서 확인된 사항을 신규 설계에 반영했습니다.

| 기존 문제 | 신규 설계 대응 |
|---|---|
| 위치 동기 트리거 경로 미구현 (`CAjinTrigger` 미인스턴스화) | periodic mode 하드웨어 트리거 경로 명시 |
| 소프트웨어 `Sleep(100)` 토글 트리거 | HW 위치주기 비교기 — 소프트웨어 개입 없음 |
| `StartTrigger()` 최대 10발 (버퍼 오버플로 존재) | 버퍼 미사용 — 트리거 개수 무제한 |
| 피치 양자화 미검토 | UPP를 피치의 정수 약수로 설계 단계에서 확정 |
| 트리거 펄스 폭 미확인 | 2 µs 명시 (카메라 최소 1 µs) |
| 엔코더 전송 노이즈 내성 | 차동(HPC4L) 채택 |
| 지령/피드백 경로 혼재 | 지령(AXM)과 트리거(AXC) 역할 명확 분리 |
